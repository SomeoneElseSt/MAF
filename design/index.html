Design system

How MAF looks, reads and behaves, and how to change it without it going haywire.

For agents: read this first

Every agent working on MAF reads this page before changing anything people see: templates, CSS, JavaScript, wording, or a new screen. If something here disagrees with the code, the code is what's live: say so, and ask the maintainer which one is right.

  1. The hard rule comes first. Never read what students wrote on the live site (see AGENTS.md). Design and debug only with the local server and made-up sample data. The Screens tab is made entirely from made-up data.
  2. Use what's here. Colours come from the tokens, sizes from the type scale, pieces from Components. No new colour, font, size, shadow or component without the maintainer's OK.
  3. Show 5 variations to choose from. By default, any design change starts as a local HTML page with 5 variations, each showing every state (empty, some, many; light and dark), and the maintainer picks one. Skip this only when the change is trivial, or it copies a pattern that already exists. Until the maintainer chooses, build nothing in the site itself.
  4. Wording is agreed first, on its own. Offer 3 options in plain text, no mock-up, and change every place the words appear (the form, the page, the Feed line, the guide).
  5. Show it locally before anything ships. Restart the local server after any Python, template, CSS or JS change (static files are fingerprinted at startup), check the page yourself signed in, then send the maintainer a link.
  6. Update the screens. If people will see a change, add or update its entry in design/screens.py, run it, open this page's Screens tab for the maintainer, and wait for their sign-off. A headless browser seeing it doesn't count as the maintainer seeing it.
  7. Tests stay fast. uv run pytest -q runs in about 6 seconds. Add a test for the behaviour, not a long one; keep the whole suite near 10 seconds.
  8. Release only when the maintainer says so ("release", "send it", "ship it"), one change per release, with SPEC.md, README.md and the guide or privacy page updated when what they say changed.
  9. Talk to the maintainer in plain language. What changed or what needs deciding first, one thing at a time, how only when asked.

Principles

Each one comes from the maintainer's feedback while MAF was built. When two pull against each other, the earlier one wins.

  1. Anonymity shapes the design. No usernames in lists, no profiles to follow. People appear as a two-word name that changes per thread. Nothing on a screen should help guess who wrote something.
  2. Quiet and text-first, never "vibecoded". It should read like a well-set page of text (think Hacker News or LessWrong), not an app template. No cards, gradients, pill buttons, icon rows, hero sections, decorative emoji or drop shadows (floating menus excepted). If it looks like every other generated site, it's wrong.
  3. Consistency over novelty. Reuse an existing pattern (the grey notice, the centred pop-up, a meta-line action, the soft button) before inventing one. The same relationship gets the same gap everywhere: if Pinned sits 26px above its rows, so do Today, New and Profiles.
  4. Nothing jumps. Changing a selection, a count or a state must not move anything around it. Sort options reserve their bold width; the Feed count always has room for two digits; dates keep their place.
  5. Always show it's working. A button that sends something greys out and says what it's doing ("Posting…", "Replying…", "Sending…") until the page answers.
  6. Never break Back. Back and Forward (including mouse buttons) go to the previous page, never to a previous state of the same page. Forms on a thread send in the background and stay out of the history unless marked as an exception.
  7. Light and dark mirror each other. Each dark colour is 255 minus its light value, so every tone keeps the same distance from the background. Exceptions are listed under Colour.
  8. One accent. Ember (--hot) marks #hottakes, New and NSFW. The Dates rose is the only other colour, and only on Dates. Colour is never the only signal: the hot tag is also underlined.
  9. Plain words, few of them. See Writing. "Too verbose" is the most common correction.
  10. Works without JavaScript, except sign-in, private replies and Dates (they need encryption in the browser).

Type

Serif for reading, sans for the interface. Titles, post text, replies, headings and pop-up text are serif. Everything you operate or that describes something (header, buttons, details lines, labels, help, notes, errors, empty states, notices about a reply) is sans. Using the serif for an interface note is the classic mistake here. No web fonts: system stacks only.

  • Weights: 400, and 600 for titles, labels, the selected sort and badges. 700 only on the wordmark. Bold in running text only through Markdown.

Layout and spacing

  • One centred column, 700px wide, 20px side padding. The footer sits at the bottom on short pages. The scrollbar's space is always reserved, so pages don't shift.
  • Phones are anything 560px or narrower; 380px is the smallest checked (and 320px for the header). On phones the header becomes two rows: MAF, Submit, then Dates, NSFW, Dark on the right; search and Feed below.
  • Header order, left to right: MAF, Submit, search (with #), Feed, Dates, NSFW, Dark. The words share one size and one gap.
  • Section headings (Pinned, New, Today, Profiles): 26px above, 6px below. Rows: 8px top and bottom.
  • Notices: 16px by 18px inside, 30px above, 24px before a form that follows.
  • Replies indent 26px per level (16px on phones). A reply box indents one step under what it answers; an edit box replaces the text in place, with no indent.
  • A button sits 18px under the last line of text above it, whether that's a box or plain text.
  • Small controls keep a 24 × 24px tap area without looking bigger.

Components

The live examples use the site's real classes. Reach for these before writing new CSS.

Buttons

.button is a soft fill (the tint), with a border only on hover. .button.plain is the secondary action: just grey text. One soft button per row. While sending: disabled, and the label says what's happening (data-pending). Inside a grey notice the soft button sits on the page colour.

Writing

  • Short and plain. One idea per sentence, everyday words, no jargon. If it can lose a sentence, it should.
  • Say what happened and what the person can do: "That code didn't match. Check the 6 digits, or ask for a new code."
  • Talk to the person as "you". MAF is "MAF", never "we" pretending to be a team.
  • Sentence case. Two-word actions about the post itself are Title Case (Flag Post, Hide Post, Flag Profile), and so are the footer links (User Guide, Source Code, Sign Out). Header words start with a capital (Submit, Feed, Dates, NSFW, Dark).
  • Buttons in progress use the verb and an ellipsis: Posting…, Replying…, Saving…, Sending….
  • No emoji in interface text ("Request deletion", not "Request nuke ☢️"). No "Oops", no exclamation marks, no cute.
  • Examples and placeholders are generic but meaningful: real-sounding situations from student life, never "example.com" or a contested opinion.
  • Never put a real name in an example. Warnings about names say "names someone", not who.
  • The same thing has the same name everywhere: in the form, on the page, in the Feed and in the guide.

Accessibility

  • WCAG AA: text 4.5:1 on paper, tint and the washes; input borders 3:1. Check both themes and both tinted sides.
  • Never colour alone: the hot tag is underlined, Flagged is bold as well as red.
  • Visible focus everywhere: a 2px ink outline. Keyboard users get a Skip to content link.
  • 24 × 24px tap areas for small controls.
  • Respect reduced motion: transitions switch off.
  • Changes made without a reload (pins, live replies) are announced in an aria-live region.

Where things live

  • maf/static/style.css: the one stylesheet. Tokens at the top; dark mode right after.
  • maf/templates/: Jinja pages. base.html is the header and footer for all of them.
  • maf/static/*.js: small vanilla scripts, one job each. No frameworks, no build step, no inline scripts (the Content-Security-Policy forbids them).
  • maf/housetags.py: house tags' outlines and etiquette. maf/profiles.py: Dates questions and answers.
  • SPEC.md: how everything behaves, in detail. README.md: what MAF does and the privacy audit.
  • design/: this page, and screens.py, which makes the Screens tab.
